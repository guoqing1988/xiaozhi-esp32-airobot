# Arduino 按需诊断实施计划

> **执行要求：** 使用 `superpowers:executing-plans` 按任务执行；除用户明确要求，不派发子代理。先完成代码 review，再补充和 review 测试、执行验证，最后更新文档。

**目标：** 不进行周期检测，通过 Web 主动检测 ESP32 ↔ Arduino 双向通信，并测试单次舵机命令，准确展示结果，避免干扰 AI、音频和遥控。

**架构：** 复用现有 UART、接收任务、WebSocket 及日志通道；新增统一 UART 发送任务及有界发送调度，普通控制和诊断均通过它发送。停止优先，摇杆旧状态覆盖，发送任务以外不等待 UART；Arduino 增加兼容旧命令的短诊断协议，ESP32 使用固定容量的单笔诊断状态和增量行解析器。Web 立即收到受理响应，通过现有按需请求查询该笔结果；超时为“未知”，不自动重发。正常控制保留现有协议和行为，不声称诊断确认覆盖所有 AI/Web 正常控制命令。

**技术栈：** ESP-IDF 6.0.2、FreeRTOS UART、Arduino AVR、C++、现有 HTTP/WebSocket 与原生 JS、Python 主机测试。

**设计依据：** 本次对话已确认的按需诊断需求；本文件同时作为本次功能的设计依据。

## 全局约束

- 默认无诊断心跳，无自动探测、自动运动、自动重试；不新建诊断专用常驻任务。
- 仅支持无动作连接检测和舵机角度测试；不新增自动电机运动测试。现有停止功能不受影响。
- 无 TF 卡编译变体必须保留 Web 页面、机器人控制、按需诊断和日志，以及不依赖 TF 卡的拍照/视频；禁用文件上传、歌曲、持久化闹钟和相册功能。TF 卡变体即使未插卡也应启动非存储 Web 功能。
- 一次最多一笔诊断；固定尺寸状态与行缓冲，不引入无界队列；满载直接返回忙。
- Web/AI 主循环、音频任务不得等待下位机；不改共享音频与协议核心；不增加 UART0 诊断日志。
- UART 写入仅在统一发送任务执行；AI/Web 只向固定容量调度器非阻塞提交，满时返回忙；不持共享锁调用可能阻塞的 UART API。停止优先且清除旧摇杆待发状态，不能打断已在途字节或 Arduino 当前阻塞动作。
- 请求 ID 和启动世代须关联，避免迟到回执被匹配到新请求；不复用普通命令文案推断成功。
- 检测收到回复只证明本次双向链路有响应；舵机“已处理”不代表硬件实际到位。
- 不改接线、NVS 键、现有板身份；两端固件必须更新；普通控制向旧固件保持兼容，旧固件诊断超时提示不支持或链路未知。
- 高峰期失败、写不进 UART、HTTP 异常及 Web 断连时均不无限占用状态；不中断现有停止命令。
- 不新增全局依赖、不读取敏感文件、不直接编辑生成文件；不调用付费接口。

## 审查重点

1. UART 回执任意拆包、粘包、超长帧及干扰文本：不越界，后续完整行可恢复。
2. 超时后迟到回执、序号回绕和 Arduino/ESP32 单侧重启：旧结果不更新当前请求。
3. 诊断期间其他 Web/AI 命令和停止并发：不造成数据竞争、长期阻塞或重排；限额失败可见。
4. 仅单向线路断开、下位机不支持新协议和 Web 断开：反馈未知/超时，不谎称成功或执行失败。
5. UNO SRAM、内部 SRAM 最大连续块和关键任务栈：先测基线与峰值，未真机测量不声称零影响。

## 文件与职责

- `main/boards/bread-compact-wifi-s3cam-airobot/arduino/MecanumRobot/MecanumRobot.ino`：诊断命令解析、响应和限长处理。
- `main/boards/bread-compact-wifi-s3cam-airobot/compact_wifi_board_s3cam_airobot.cc`：UART 增量接收、诊断单笔状态及同步。
- `main/boards/bread-compact-wifi-s3cam-airobot/http_upload_server.{h,cc}`：板级回调及 WebSocket 按需请求；不等待回执。
- `main/boards/bread-compact-wifi-s3cam-airobot/web/index.html`：主动诊断及单次舵机测试 UI。
- `scripts/tests/`：项目既有主机测试入口；必要时新增可实际编译运行解析器/协议的宿主测试，而不是只复制逻辑。
- `main/boards/bread-compact-wifi-s3cam-airobot/README.md` 与 `arduino/MecanumRobot/README.md`：协议、状态、资源限制、烧录及人工测试。

## 任务 1：冻结协议与发送边界

- [ ] 核对 IDF 6.0.2 UART 驱动对 TX 缓冲、并发写入及非阻塞发送的真实保证；记录可用方案，不能使用 TOCTOU 方式假装非阻塞。
- [ ] 确定请求和回执格式、ASCII 上限、整数 ID 编码、错误码、超时与重启关联规则。连接检测无物理动作，舵机诊断必须显式指定 0–180 度；报文与现有 `@` 行协议兼容。
- [ ] 明确旧版 Arduino 不响应时为未知/超时，而非误判离线；明确结果查询只读取固定状态，不触发再次发送。
- [ ] 使用统一发送任务实现有界调度：有限普通队列、覆盖式摇杆槽与独立停止槽；编写可验证的并发、队列满、停止优先和摇杆过期测试，确认正常调用方不等待 UART。

## 任务 2：Arduino 诊断协议

- [ ] 先编写协议回归测试：连接检测无电机/舵机动作；合法舵机测试只执行一次；越界、未知指令返回拒绝；长帧丢弃并恢复；不会重复执行；普通 `go/drive/servo` 分发不变。
- [ ] 在 UNO 固件中添加固定缓冲的按需请求解析与短回执，不加动态字符串、周期任务或心跳；接收确认与处理结果语义分开。
- [ ] 确保不改变 `drive-stop`、巡线及既有普通指令处理；不声称旧的阻塞动作期间仍能及时响应诊断。
- [ ] 使用现有 `arduino-cli` 与仓库要求的 RX 配置编译，记录 Flash 与 SRAM；对照改动前版本，不烧录。编译依赖不可用时如实记录。

## 任务 3：ESP32 接收与诊断状态

- [ ] 先编写实际解析代码的主机测试：逐字节、任意分割、多行、63 字节以上、噪声、超长后恢复；`@busy/@done/@stat` 不回归。
- [ ] 实现固定长度增量行解析器，正常保留跨读半行；超长整行丢弃至换行并计数，禁止截断后误作有效报文。
- [ ] 实现单笔状态机：受理、发送、确认、处理/拒绝、超时/未知；检查 ID 与世代，迟到或重复回执不匹配新请求；调用方不等待。
- [ ] 确保并发保护覆盖 AI、Web 发送与防抖共享状态；统一发送任务独占 UART 写入且不持共享状态锁等待 UART。普通控制的返回明确为已排队而非已执行。
- [ ] 补测写失败、忙、超时、重复请求、单向断线模拟、重启及并发；检查接收任务创建失败和内存不足时的诊断反馈。

## 任务 4：Web API 与界面

- [ ] 增加独立的诊断开始与结果查询 action；按 ID 查询，参数和角度严格校验，JSON 用现有 cJSON 正确转义；忙/不可用/非法参数返回真实失败。
- [ ] 界面提供“检测连接”和显式的舵机角度单次测试；显示请求状态、响应耗时及可理解的超时原因，说明不能证明实际运动。
- [ ] 仅在有一笔待完成请求时短暂按需查询，停止于完成、超时、断线或离开页面；不得启动永久心跳。断连后允许有限期限内按 ID 查询原结果，不自动重发命令。
- [ ] 测试双击、Web 断开重连、超时、失败、旧固件、不同状态显示；先语法和构建校验，再按项目 web-access 规范验证实际可见性和交互。
